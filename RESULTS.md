# Results

Sections 1-6 use English Premier League 2023-24 data (100 matches, 20 teams); section 7 uses Olist e-commerce data.
LLMs: Gemini 2.5 Flash (`gemini-2.5-flash`) and `openai/gpt-oss-120b` served by Groq.
The paper used GPT-4.1-mini. Run dates: 2026-11-18 to 2026-11-21.

## Key findings

- **The paper's main result reproduces exactly.** Manual-only 7/16, manual-expanded 16/16 and manual + LLM 16/16 (+128.57%), batch by batch, using the authors' models, tests and anomalies.
- **Free LLMs match GPT-4.1-mini on the paper's benchmark.** Manual tests plus tests generated by Gemini or by gpt-oss-120b also catch 16/16.
- **Most generated tests add nothing.** Pruning keeps 18 of 58 candidate tests (Gemini) and 19 of 54 (gpt-oss-120b) with no loss of detection across 188 mutated databases, so roughly two thirds of the tests can be removed. The paper's manual audit judged 16 of 25 tests redundant or low-value.
- **A minimal test set does not transfer to unseen damage.** When the minimal set is chosen without seeing out-of-range, orphaned-row and date-shift damage, it catches only 33.3% (Gemini) and 40.0% (gpt-oss-120b) of what the full candidate set catches on that damage. Rotating every operator out in turn gives an average of 46.0% (Gemini) and 44.0% (gpt-oss-120b). The expectation that "the full set adds no extra coverage" does not hold on unseen mutation types.
- **On a second domain (Olist), the transfer problem is far worse.** A minimal set chosen without seeing out-of-range, orphaned-row and date-shift damage catches 2.7% (Gemini) and 2.9% (gpt-oss-120b) of what the full set catches on that damage (football 33.3% and 40.0%), and pruning keeps 57 of 73 and 56 of 72 tests instead of about a third. 15 and 17 generated tests fail on the real, clean Olist data.
- **Detection on the paper's benchmark is stable, the tests are not.** Over five trials manual + LLM is 16/16 every time (frozen and freshly regenerated), as in the paper, yet each fresh generation shares only 78-94% of its tests with the first one, and a changed prompt dropped out-of-range coverage from 24/24 to 12/24.

## 6. Stability (five trials)

Two kinds of repetition, following the paper's five-trial protocol:
- **Frozen**: the same generated test set, anomaly experiment run five times.
- **Fresh**: tests regenerated from scratch for every trial (new LLM call per model), then the anomaly experiment.

Paper: 7/16, 16/16, 16/16 in all five trials.

| LLM | Mode | Manual-only | Manual-expanded | Manual + LLM |
|---|---|---|---|---|
| gpt-oss-120b | Frozen, 5 runs | 7, 7, 7, 7, 7 | 16, 16, 16, 16, 16 | 16, 16, 16, 16, 16 |
| gpt-oss-120b | Fresh, 5 trials | 7, 7, 7, 7, 7 | 16, 16, 16, 16, 16 | 16, 16, 16, 16, 16 |
| Gemini 2.5 Flash | Frozen, 5 runs | 7, 7, 7, 7, 7 | 16, 16, 16, 16, 16 | 16, 16, 16, 16, 16 |
| Gemini 2.5 Flash | Fresh, 5 trials | 7, 7, 7, 7, 7 | 16, 16, 16, 16, 16 | 16, 16, 16, 16, 16 |

How much the generated test sets change between fresh trials:

| LLM | Tests kept per trial | Identical to trial 1 |
|---|---|---|
| gpt-oss-120b | 52, 53, 56, 53, 55 | 52, 47, 46, 46, 47 |
| Gemini 2.5 Flash | 53, 67, 62, 62, 53 | 53, 52, 50, 53, 50 |

- **Detection on the paper's benchmark is fully stable**, for both LLMs and in both modes, matching the paper.
- **The test sets themselves are not stable.** Between 6% and 22% of the tests in a later trial are not in trial 1 (gpt-oss-120b keeps 46-47 of trial 1's 52; Gemini keeps 50-53 of trial 1's 53, and its set size ranges from 53 to 67). The 16-anomaly benchmark is too coarse to show this; the mutation results in sections 3-5 do show it (out-of-range coverage 24/24 vs 12/24).
- The frozen runs use the latest test sets (after the date-range change), so manual + LLM is 16/16 for those sets as well.
- The first Gemini attempt at fresh trial 5 stopped because the Gemini API returned 503 (model overloaded); the rerun completed all five trials (trials 1-4 came from the reply cache, so they are the same generations).

## 7. Second domain: Olist e-commerce

Data: Olist Brazilian E-Commerce (Kaggle), 99,441 orders, of which a fixed hash-based sample of 5,000 orders is used. Five models: dim_customers (5,000 rows), dim_products (3,831), dim_sellers (1,216), fct_orders (5,000), fct_order_items (5,685). Manual baseline: unique and not null on each model's key (10 tests). 427 mutated databases (same seven operators; two seeds instead of three).

The first gpt-oss-120b generation lost fct_orders to Groq's rate limit (HTTP 429); the numbers below come from a rerun that covers all five models.

| | Gemini 2.5 Flash | gpt-oss-120b |
|---|---|---|
| Generated tests kept / rejected | 88 / 1 | 89 / 0 |
| Fail on clean data (broken) | 15 | 17 |
| Mutants caught by all candidates | 335/427 (78.5%) | 319/427 (74.7%) |
| Generated tests: useful / redundant / low-value / broken | 51 / 18 / 4 / 15 | 50 / 15 / 7 / 17 |
| Minimal set (of working candidates) | 57 of 73 | 56 of 72 |
| Fixed held-out: kept set catches | 4/192 (2.1%) | 4/192 (2.1%) |
| Fixed held-out: all candidates catch | 148/192 (77.1%) | 140/192 (72.9%) |
| Kept set as share of full set on held-out | **2.7%** | **2.9%** |
| Leave-one-operator-out average | **43.3%** | **44.7%** |

Per operator, caught by all candidates (Gemini / gpt-oss-120b): date_shift 28/48 / 24/48, double_count 15/15 / 15/15, duplicate_key 20/20 / 20/20, invalid_category 32/32 / 24/32, null_injection 120/168 / 120/168, orphaned_child 16/16 / 16/16, out_of_range 104/128 / 100/128.

- **Pruning removes much less on richer data.** On football about two thirds of the candidates could be dropped; on Olist the minimal set still needs 57 of 73 working tests (Gemini) and 56 of 72 (gpt-oss-120b), because five tables and 42 columns give most tests something unique to catch.
- **The transfer problem is far worse.** A minimal set chosen on nulls, duplicate keys, invalid categories and double counting catches only 4 of 192 out-of-range, orphaned-row and date-shift mutants with either LLM (2.7% and 2.9% of what the full set catches; football: 33.3% and 40.0%). The likely reason (not yet checked test by test) is that the range and date tests that catch the held-out damage catch nothing extra in the selection operators, so pruning drops them. Rotating every operator out gives about the same average as football (43.3% and 44.7% vs 46.0% and 44.0%).
- **Generated tests now fail on clean data.** 15 Gemini tests and 17 gpt-oss-120b tests fail on the real, unmodified data (none did on football). Real data has real quirks: for example 13 sampled orders whose payments differ from items plus freight by more than 1, and one delivered order without a delivery date. Which of these failures are real data issues and which are wrong tests has not been checked yet.

## 8. Scoring speed and correctness check

The standard scoring engine starts dbt once per mutated database (parse the project, connect, run every test), which took about 14 minutes for the 188 football databases on a laptop. The fast engine compiles the tests once with dbt and runs the compiled SQL directly in DuckDB, wrapped the way dbt wraps a data test.

| Check | Databases | Test results compared | Differences from dbt |
|---|---|---|---|
| Football, manual + Gemini tests (58) | 189 (188 mutated + clean) | 10,962 | 0 |
| Olist, manual + Gemini tests (88) | 428 (427 mutated + clean) | 37,664 | 0 |

A full fast scoring run of 73-87 tests on the 427 Olist databases took 45-49 seconds on the same laptop. `scoring.run` uses the fast engine by default; `--engine dbt` keeps the original path, and `python -m scoring.verify_fast` repeats the comparison.

## Notes on comparability

- The paper judged usefulness by hand against 16 anomalies; here it is computed automatically against 188 mutated databases, so the counts are comparable in spirit, not one to one.
- Data differs slightly from the paper's setup: the same 100 matches were fetched round by round with TheSportsDB's current free key, and status `FT` is mapped to `Match Finished`.
- LLM calls use temperature 0.
